# Use a custom binary synchronization protocol

Codejeet will implement a versioned binary codec alongside its custom CRDTs rather than use JSON or a general-purpose binary format. A version 1 frame contains the four ASCII magic bytes `CJET`, a one-byte version, a one-byte message type, a canonical unsigned-LEB128 payload length, the payload, and a four-byte big-endian CRC32C covering every preceding byte. The 64 KiB limit includes the complete envelope. The decoder performs safe structural length checks, verifies the checksum, and only then parses CRDT payloads. Actor IDs are 16 random bytes, counters and revisions are unsigned 64-bit values encoded with canonical LEB128, batches are limited to 100 changes, and version 1 has no application-level compression.

Problem Notes preserve well-formed Unicode text exactly, with no trimming, newline conversion, or normalization, within both 2,000 UTF-16-code-unit and 8 KiB UTF-8 limits. Empty text emits an explicit delete mutation, while invalid Unicode is permanently rejected and replaced with canonical state. Problem Note local revisions are scoped to an actor and problem.

Authenticated WebSockets perform bootstrap before becoming live, HTTP provides recovery using the same binary protocol, snapshot frames stream in deterministic order into temporary storage, and each account retains at most 64 permanent replica identities. `SNAPSHOT_BEGIN` declares revision, counts, and total length; `SNAPSHOT_END` carries the CRC32C accumulated over the concatenated canonical record bytes, excluding frame headers and frame checksums. Compact binary rejection codes distinguish internal recovery actions but never appear in Codejeet's interface; Clerk and Google may still display their own authentication messages. Explicit sign-out closes authenticated sockets and prevents further transmission before switching every tab to the Public View, while leaving each account's IndexedDB cache and pending changes intact.

The same-origin WebSocket upgrade authenticates from Clerk's secure session cookie, validates the exact allowed origin, derives the Clerk user ID server-side, and never accepts identity in protocol payloads or URLs. The server closes each connection at token expiry; Clerk refresh and a complete new bootstrap are required to resume synchronization, but temporary authentication loss does not deactivate the local Account Cache. An account may have at most 16 concurrent sockets and an actor at most 8, with excess connections closed before bootstrap.
