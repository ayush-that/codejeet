# Coordinate synchronization with Durable Objects and D1

Codejeet will synchronize IndexedDB Account Caches with a delta-state protocol while keeping D1 as canonical durable server storage. One Durable Object per learner account will authenticate mutations, serialize them through an explicit FIFO queue, commit each mutation with a transactional D1 batch, and broadcast only after persistence; it will not hold `blockConcurrencyWhile()` across D1 network I/O and can reconstruct its coordination state from D1 after restart. Every accepted logical mutation receives a unique account-wide unsigned 64-bit server revision, allocated contiguously inside the transaction.

The existing OpenNext application gains a thin custom Worker entry that handles synchronization routes, derives the account Durable Object name from an HMAC of the verified Clerk user ID, and delegates all other requests to the generated OpenNext handler. Wrangler provisions the class as a SQLite-backed namespace through a `new_sqlite_classes` migration so an emergency deployment rollback does not require converting the Worker to declarative Durable Object exports. D1, rather than Durable Object storage, remains the Account Data system of record.

D1 stores one logical Progress OR-Set per account, physically divided into deterministic hash-prefix shards that split before their canonical encoding exceeds 48 KiB, one current Problem Note register per account and problem, bounded per-note and per-actor highest accepted local revisions, and separate actor causal state. A shard split and directory update occur atomically, and version 1 never merges shards. Every Progress add and removal consumes one actor counter: an add stores that dot with the element, while a removal advances causal context without retaining its operation dot as a live element and removes only the live dots it observed. A Problem Note local revision is scoped to its actor and problem; stale or repeated revisions return the current canonical register without allocating another server revision. Canonical note values are validated UTF-8 bytes stored as D1 BLOBs, while the register separately records value or deletion, server revision, winning actor, and winning local revision. Progress deltas may be joined before transmission when the join preserves add dots, observed removals, and causal context.

Bootstrap enters the mutation queue, captures revision `R`, and streams a deterministically ordered Canonical Snapshot into a temporary IndexedDB generation without assembling the complete snapshot in one buffer. Server mutations wait until snapshot streaming finishes, then resume and accumulate in a bounded per-connection catch-up buffer. After the client validates the manifest, counts, lengths, and checksum and confirms its atomic generation switch, the server sends the buffered deltas and marks the connection live; an overflowing catch-up buffer restarts bootstrap.

The catch-up buffer is limited to 100 logical changes or 1 MiB of encoded frames, whichever comes first. Snapshot framing uses a `SNAPSHOT_BEGIN` frame for the revision, counts, and declared length, deterministic record chunks, and a `SNAPSHOT_END` frame for the final incremental checksum. The complete-snapshot checksum covers the concatenated canonical record bytes independently of chunk boundaries.

Connections use the Durable Object Hibernation WebSocket API. Each socket attachment contains only its actor ID, authentication expiry, handshake phase, and acknowledged revision. One Durable Object alarm tracks the earliest connected session expiry, closes every expired socket, and reschedules itself; expiry is also checked on every request and message.

A connection authenticates, registers or validates its Actor and Revocation Handle, uploads and acknowledges its existing pending batches, receives and atomically installs a Canonical Snapshot, confirms installation, consumes buffered catch-up deltas, and only then becomes live. Local edits created during bootstrap remain in the Pending Overlay and transmit after the connection becomes live; the interface never waits for handshake progress.

Versioned compatibility endpoints route older clients through the same canonical model during migration. A reserved server-managed legacy actor, outside the 64-installation limit, converts legacy endpoint intent into canonical mutations. The adapters remain until deployment telemetry shows no legacy traffic beyond the supported lifetime of an old browser tab.

After three consecutive WebSocket connection failures, the client uses an authenticated HTTP recovery path carrying the same binary frames through the same validation, queue, acknowledgement, and streamed-snapshot machinery. It continues capped WebSocket retries, and a restored socket performs a new complete bootstrap before becoming live.

The server validates every logical change in a batch before modifying D1. A permanent item failure rejects the entire batch and identifies its item index; the client discards and canonically replaces only that item, then retries the remaining changes separately. Transient persistence failure produces no acknowledgement and leaves every pending mutation intact.

Record-level permanent rejection, including invalid slugs, notes, dots, and counters, discards only the affected pending record. Session-level incompatibility, including an unsupported protocol, unavailable IndexedDB schema, lost authentication, or unknown future server state, preserves the complete Account Cache and Pending Overlay for later recovery.
